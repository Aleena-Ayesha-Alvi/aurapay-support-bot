# 💳 AuraPay Enterprise Support Agent

A customer-support chatbot for **AuraPay**, a fictional enterprise payment gateway. It answers merchant questions about compliance, chargebacks, APIs, privacy, SLAs and escalations **using only the company's own policy documents**, cites the exact document and section for every answer, and remembers the whole conversation. Built with Retrieval-Augmented Generation (RAG).

**🚀 Live Demo:** https://aurapay-support-bot-5d92t5d3lshhnwnzlinoba.streamlit.app/

## What It Does

- **Answers from documentation only.** Six internal policy documents form the knowledge base. If the answer isn't in them, the bot says so instead of guessing.
- **Cites its sources.** Every documentation-based answer ends with the source file and section it came from.
- **Remembers the conversation.** Follow-ups like "that volume" or "that dispute" are understood, and facts you share (your name, processing volume) are recalled many turns later.
- **Shows its evidence.** The retrieved chunks behind each answer can be inspected in the UI.

### Knowledge Base

| Document | Covers |
|---|---|
| `1_kyc_aml_compliance.md` | Merchant identity tiers, prohibited businesses, SAR transaction monitoring |
| `2_chargeback_dispute_resolution.md` | Chargeback lifecycle and fees, evidence requirements, arbitration |
| `3_api_integration_guidelines.md` | OAuth authentication, rate limits, webhooks |
| `4_gdpr_data_privacy.md` | Right to be forgotten, access requests (DSAR), breach notification |
| `5_merchant_sla.md` | Uptime guarantees, maintenance windows, SLA compensation |
| `6_support_escalation_matrix.md` | Tier 1 / 2 / 3 support responsibilities and escalation rules |

The documents are generated by `setup_docs.py`, which also appends an "EU region" variant of each so the retriever has to cope with near-duplicate content.

## How It Works

```text
User question + full chat history
          │
          ▼
① History-aware query rewriting (LLM)
   "What about /v1/charges?" → "What is the rate limit for the /v1/charges endpoint?"
          │
          ▼
② FAISS vector search (MMR, k=7 of 20 candidates)
   over 36 header-aware chunks embedded with all-MiniLM-L6-v2
          │
          ▼
③ Grounded answer generation (LLM)
   chunks are passed WITH their [source_file | Section] labels
          │
          ▼
Answer + "Source Document / Section" citation + inspectable chunks
```

**Indexing.** Each Markdown document is split first by its `#` / `##` headers (so every chunk knows its document title and section) and then into ~1,000-character pieces with 100-character overlap. The 36 chunks are embedded locally with the `all-MiniLM-L6-v2` sentence-transformer and stored in a FAISS index. The index is committed in `faiss_index/` for instant start-up and rebuilt automatically if deleted.

**① Query contextualisation.** A LangChain history-aware retriever rewrites each new question into a standalone search query using the chat history. This is what makes follow-ups like "that volume" or "that specific dispute" retrieve the right passages.

**② Retrieval.** Maximal Marginal Relevance (MMR) picks 7 chunks out of the 20 most similar, balancing relevance with diversity. This matters because the knowledge base contains near-duplicate EU-region sections.

**③ Grounded generation.** The answer prompt enforces a few rules:
- Policy questions are answered only from the retrieved context. Otherwise the bot replies with the fixed fallback *"I do not have that information in my current documentation."*
- Facts the user shared earlier in the chat (name, volume) may be used from history.
- Every documentation-based answer must end with the **Source Document** and **Section**.

Each chunk is prefixed with its `source_file` and `Section` metadata before it reaches the LLM, so citations always name real documents.

**Memory.** The full conversation is sent on every turn. That covers 12+ turn sessions reliably. For much longer sessions, a sliding window or summarised memory would keep the rewritten queries focused.

## Tech Stack

| Layer | Technology |
|---|---|
| UI | Streamlit (chat interface) |
| LLM | GPT-4o mini via [AI Pipe](https://aipipe.org) (OpenAI-compatible), LangChain `ChatOpenAI` |
| RAG framework | LangChain (`create_history_aware_retriever`, `create_retrieval_chain`) |
| Embeddings | `sentence-transformers/all-MiniLM-L6-v2` (runs locally, CPU) |
| Vector store | FAISS with MMR retrieval |
| Chunking | `MarkdownHeaderTextSplitter` + `RecursiveCharacterTextSplitter` |

## Run Locally

Requires Python 3.12.

```bash
python -m venv .venv
.venv\Scripts\activate           # Windows  (macOS/Linux: source .venv/bin/activate)
pip install -r requirements.txt  # installs CPU-only PyTorch for the embedding model
```

Copy `.env.example` to `.env` and add your [AI Pipe](https://aipipe.org) token:

```env
AI_PIPE_KEY=your_aipipe_token
# Optional: any OpenAI-compatible provider works
# LLM_MODEL=gpt-4o-mini
# LLM_BASE_URL=https://aipipe.org/openai/v1
```

```bash
streamlit run app.py
```

The embedding model downloads on first launch.

## Deploy to Streamlit Cloud

1. On [share.streamlit.io](https://share.streamlit.io), click **Create app**: repository `aurapay-support-bot`, branch `main`, main file `app.py`.
2. In **Advanced settings**, choose Python **3.12** and add the secret `AI_PIPE_KEY = "your_aipipe_token"`.
3. Click **Deploy**. The first boot takes a few minutes while PyTorch and the embedding model install.

## Testing

A single continuous 13-turn conversation tests base retrieval, follow-up memory, technical accuracy, abrupt topic switches, long-term recall of the user's name, the GDPR-vs-AML legal conflict, escalation policy, out-of-domain refusals and citation accuracy. **13 / 13 turns pass.** See [QA_testing_protocol.md](QA_testing_protocol.md) for every question, answer and citation, plus engineering notes on the fixes.
